# Проверка кандидата,29.10.2026

**Нагрузочная и пограничная серия завершена. Релизная приёмка не пройдена: достаточный запас памяти не подтверждён, общий mixed graph ещё не реализован.** Старый checkout и его автозапуск сохранены; кандидат работает только наGPU0–1,localhost8086. GPU2–3 не используются. Действующий unit указан в `кандидат/state/acceptance/active-unit`.

## Что изменено

- Сокращён lifetime временных MLP-буферов, NCCL workspace выделяется по необходимости. Captured storage сохраняется при росте, чтобы replay не обращался к освобождённому адресу.
- Исправлен admission вытесненного запроса: учитывается полный требуемый attention-контекст, а для rolling GDN — потребность текущего chunk. Это устраняет повторный пересчёт без возможности продолжить decode.
- Включены отдельные адреса чтения/записи свёрточного состояния на границе KV-страницы. Проверка49147-token input с длинным продолжением улучшилась с1/8 до8/8 правильных начальных и конечных кодов.
- Отдельный opt-in Triton kernel объединяет целочисленный расчёт convolution metadata.48 exact parity случаев и CUDA graph replay прошли; standalone wall-time снизился с315–324 до33–38мкс. Сквозное ускорение модели не подтверждено; режим оставлен выключенным.

Контекст262144,maxseq16,batch8192,KV11295047936байт/GPU,MTPK4 и веса сохранены. Готовый внешний DFlash2 не добавлен, новый драфтер не обучался, дополнительная квантизация не вводилась.

## Что не принято как улучшение

MLP chunks1024 остаются выключенными: изменились один короткий текст, вероятности Clef до0,0051 и результат одного solo/mixed state case. Рост C1 до133,9token/s сопровождался ростом MTP acceptance до2,587 accepted/draft против1,753; его нельзя считать чистым ускорением ядер с прежним распределением.

В пяти исходных A/B-парах memory-runtime не изменил короткие ответы/вероятности, но интервалы throughput включают1. Для C1 ratio0,9956,95%интервал[0,9375;1,0573]. Это не подтверждённое ускорение и не статистическое доказательство нулевой просадки. Эти пары относятся к memory-runtime до последующих scheduler/convolution изменений. [A/B](AB_VALIDATION.md).

На финальном service cgroup `max/oom/oom_kill=0`,host guard не срабатывал,конечный health=200. Минимум MemAvailable хоста19,29GiB,пик memory.peak около20,00GiB при MemoryMax21GiB. File cache включён в эти числа;memory.high срабатывал и выполнялся reclaim.

**Исправление измерения VRAM:** ранняя оценка `total-used` не учитывала465MiB driver-reserved и была неверна. Прямая серия NVML с шагом200мс после изображений дала минимум **9MiB free наGPU0 и5MiB наGPU1**,без OOM в этом прогоне. После mixed workload free вырос примерно до1753/2119MiB. Driver free не равен повторно используемому кэшу PyTorch;точные allocator reserve/fragmentation под пиком ещё не измерены. Ни достаточный запас512MiB,ни невозможность будущего OOM не доказаны.

В startup-журнале остаётся прежний ERROR проверки недоступного upstream FA2,такой же в baseline. Vision encoder выбирает TORCH_SDPA,текстовая модель — собственный FA2_SM70. Это не новый fatal runtime failure;не смешивать его с CUDA OOM/illegal access,которых в финальной серии не найдено.

## Оставшиеся ограничения

- Общий mixed CUDA graph ещё не реализован. Несколько секунд пауз при Clef остаются; исправление metadata само по себе не устраняет длительные mixed steps.
- На насыщенном KV сохраняется ожидание свободной страницы: последний C8×(49147+2048) завершился8/8,но maxgap35,34с. CPU-проба страниц8192 вместо16384 убрала эту фрагментацию; GPU-приёмки и изменения runtime ещё нет.
- У двух коротких примеров есть logprob drift до0,01248 при одинаковом тексте. Все четыре semantic top20/entropy probes между conv1 Torch/fused совпали,но это не доказательство общей bitwise эквивалентности или сохранения качества во всех задачах.
- Требуются подтверждение allocator reserve на худших формах и отдельные6h/24h soak перед выпуском. Отсутствие OOM в перечисленных тестах не доказывает невозможность OOM.
