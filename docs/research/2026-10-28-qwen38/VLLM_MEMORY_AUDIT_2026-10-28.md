# Причины сбоев vLLM и ревизия выделений памяти

Дата проверки: 28 октября 2026 года. Время событий ниже — локальное время сервера, Asia/Tbilisi, UTC+4.

Последний исследованный сбой вызван CUDA OOM в первом слое модели: операция распаковки результата обмена между GPU пыталась выделить дополнительный тензор размером 80 МиБ. Стек, размер выделения и дамп планировщика согласуются с выполнением полного пакета 8192 токена без разбиения проекции на куски. Ревизия обнаружила также удержание памяти графами MTP, ненужные буферы обмена в ветке P2P и другие места роста пикового потребления.

Код и параметры рабочего сервиса не изменялись. Отчёт содержит подтверждённую цепочку последнего падения и дополнительные риски, для которых отдельно указан уровень доказательности. Нагрузочное воспроизведение на рабочих GPU не выполнялось.

## Подтверждённая цепочка падения

### Первый слой исключён из W8

В конфигурации модели `config.json:148–170` заданы исключения `-:.*\\.layers\\.0\\..*` и `model.layers.0.` / `model.language_model.layers.0.`. Первый слой остаётся вне GPTQ. Атрибут `fa2sm80_kn` устанавливается в `sm70/integrations/vllm_sm70/fa2sm80_w8.py:349` при обработке подходящего GPTQ-слоя.

В `fa2sm80_blockpipe.py:128–129` проверка `_w8` требует этот атрибут и отсутствие bias. В `:196–198` непрохождение проверки у любой из трёх проекций отправляет весь блок в `_прямо`. Стек последнего падения подтверждает именно вызов `language_model.model.layers.0` и ветку `:197`.

### Прямой блок удерживает промежуточные тензоры до down projection

В `fa2sm80_blockpipe.py:149–173` создаются `y`, `h`, `ro`, `gu`, `a`, после чего вызывается `L.mlp.down_proj(a)`. Предыдущие локальные переменные явно не освобождаются перед этим вызовом.

Для M=8192, hidden_size=5120, intermediate_size=17408 и TP=2 расчёт размеров выглядит так:

| Тензор | Расчётный размер |
| --- | --- |
| y, fp16 [8192,5120] | 80 МиБ |
| h, fp16 [8192,5120] | 80 МиБ |
| ro, fp32 [8192,5120] | 160 МиБ |
| gu, fp16 [8192,17408] | 272 МиБ |
| a, fp16 [8192,8704] | 136 МиБ |
| локальный результат down projection | 80 МиБ |
| новый результат all reduce | ещё 80 МиБ |

Сумма перечисленных живых данных в этом сценарии — около 888 МиБ, без исходных core/residual, весов, scratch, KV, кешей и графов. Это расчёт по размерам, а не замер memory snapshot. Даже освобождение только `gu` и `h` до down projection может уменьшить время жизни значительного объёма памяти, но эффект при асинхронных потоках требуется измерить.

### Rowpipe также отказывается от разбиения первого слоя

В `fa2sm80_rowpipe.py:79–85` при активном Clef и отсутствии W8 выполняется полная проекция и полное сведение:

```python
if хук_д is None or not w8:
    return tensor_model_parallel_all_reduce(layer.quant_method.apply(layer, x, bias_))
```

Строка `:85` присутствует в аварийном стеке. Следовательно, настройка размера кусков rowpipe не защищает этот путь.

### Дополнительный тензор создаётся внутри распаковки обмена

`fa2sm70_exch_i12.py:161` вызывает `e.unpack_add_i12(...)`. В `sm70/fa2_sm70/csrc/exch_i12.cu:164–178` функция выделяет `auto out = torch::empty_like(base)` в строке 171. Вход остаётся жив одновременно с выходом.

Размер совпадает с ошибкой: `8192 × 5120 × 2 / 2^20 = 80 МиБ`.

Цепочка стека:

```text
compiled model layer 0
  → fa2sm80_blockpipe._тело :197
  → _прямо :172 down_proj
  → fa2sm80_rowpipe._rowpipe :85
  → tensor_model_parallel_all_reduce
  → fa2sm70_ar2._f :336 fallback
  → fa2sm70_exch_i12._f :161
  → unpack_add_i12
  → empty_like(base), запрос 80 МиБ
  → CUDA OOM → EngineCore dead → API 500
```

## Дополнительные места с аналогичным риском

### Явный размер KV обходит автоматический бюджет памяти

**Высокий приоритет. Поведение подтверждено кодом и параметрами процесса.**

`vllm/v1/worker/gpu_worker.py:300–318`: при `kv_cache_memory_bytes` вызывается profile_run для компиляции, но затем сразу возвращается заданный размер кеша. Лог-сообщение явно говорит `skipped memory profiling` и `does not respect the gpu_memory_utilization config`.

Таким образом, уменьшение только `--gpu-memory-utilization` при сохранении явных KV bytes не пересчитает KV. Запас под крупные fallback-тензоры, новые графы и IPC нужно учитывать отдельно. Это объясняет, почему указанные 96 процентов не гарантируют 4 процента свободной памяти при реальной нагрузке.

### Ветка NCCL тоже выделяет полный результат

**Высокий приоритет. Похожий путь подтверждён статически; последнее падение произошло в P2P.**

`fa2sm70_exch_i12.py:173–184`: если copy-engine путь не подходит или не доступен, выполняется all_gather, затем тот же `unpack_add_i12`. Для TP=2 снова требуется новый тензор размера входа. При TP>2 каждое следующее сложение выделяет новый выход, пока предыдущий ещё служит входом.

Условия перехода включают отключённый P2P, неуспешную инициализацию CE, размер выше CE capacity, захват CUDA-графа. Поэтому исправление только строки 161 оставит аналогичный риск в строке 183.

### При P2P выделяется ненужный буфер all gather

**Средний приоритет. Лишнее удержание памяти подтверждено кодом.**

`fa2sm70_exch_i12.py:137–145` создаёт `свой` и `все` до проверки CE в `:151–153`. В успешном CE-пути `все` вообще не используется, но остаётся в `_КЭШ`.

Для входа fp16 [8192,5120] упаковка занимает `n/128 × 194 = 60,625 МиБ`. `все` при TP=2 занимает ещё 121,25 МиБ. Помимо этого `_ce` в `:86–89` создаёт приёмник `2 × 72 = 144 МиБ` через прямой cudaMalloc (`exch_i12.cu:245–251`), вне учёта memory_allocated PyTorch.

Итого собственные упакованные буферы 181,875 МиБ и CE-приёмник 144 МиБ сосуществуют; из них 121,25 МиБ all_gather buffer не нужны при успешном CE. Возможное исправление — ленивое выделение `все` только перед NCCL fallback. Совместимость с захватом графов и сменой ветвей обязательна.

При росте `_КЭШ` локальная переменная `б` ещё удерживает старую тройку, пока создаются новые буферы. Поэтому на первом увеличении размера временно сосуществуют старый и новый наборы. Сам словарь индексируется картой, а не каждой формой: это не доказательство прежней неограниченной утечки по формам.

### Кеш графов MTP растёт с числом сочетаний формы и контекста

**Высокий приоритет для длительной нагрузки. Удержание подтверждено кодом; вклад в OOM не измерен.**

`vllm/v1/spec_decode/eagle.py:1339–1346` создаёт `_гр_циклов`, ключ включает batch_size, input_batch_size, k, корзину max_seq_len, формы positions и hidden_states. `:1375–1391` сохраняет клоны входов и тензорных полей метаданных. `:1412` сохраняет граф и выход. В текущем файле нет вытеснения или ограничения числа записей этого кеша.

В журнале упавшего `Worker_TP0 pid=242607` есть 67 различных ключей успешного захвата графа цикла. Это наблюдение, не оценка 67 независимых полных CUDA pools: пул у графов общий, и по одному числу ключей нельзя вычислить расход VRAM.

Аналогичная структура `_гр_тела` есть в `eagle.py:629–680`: ключ дополнительно включает номер шага, записи удерживают граф, выходы и буферы. Оба режима включены в окружении текущего процесса.

Количество возможных ключей ограничивается допустимыми размерами входа и max context, поэтому корректный диагноз — кеш без собственного лимита бюджета, а не доказанная бесконечная утечка. Нужны счётчики числа ключей, retained tensor bytes и CUDA private pool usage во времени. Вытеснение нельзя реализовывать удалением буферов, пока графы ещё ссылаются на их адреса.

### Неудачный захват графа MTP оставляет уже созданные клоны

**Средний приоритет. Путь удержания подтверждён статически.**

В `eagle.py:1375–1391` клоны `d0`, `pos`, `hid`, `вх_мета` и объект `см` помещаются непосредственно в запись кеша до захвата графа. Обработчик исключения `:1433–1439` лишь ставит `мёртв=True` и возвращает None. Удаления перечисленных полей нет; повторные обращения к мёртвому ключу сразу возвращают None (`:1348–1349`), оставляя ненужные буферы жить вместе с proposer.

Исправление: безопасная очистка частично созданной записи после завершения/прерывания capture, сохранение лишь признака отказа. Нельзя без проверки пытаться продолжать работу после любого CUDA-исключения: ошибки illegal access могут повреждать весь контекст. Присутствие именно такого отказа перед последним OOM не установлено.

### Blockpipe сохраняет результаты всех кусков перед MLP

**Средний приоритет. Увеличение рабочего набора подтверждено кодом.**

В `fa2sm80_blockpipe.py:63` значение `_ВПЕРЁД` по умолчанию равно 99. В `:268–289` `_out` кладёт сведённые тензоры в словарь `сведённые`, и сначала запускаются практически все куски. Их освобождение начинается только в цикле MLP `:326–332` через pop.

Сумма только этих fp16 результатов для [8192,5120] достигает 80 МиБ, даже при небольших кусках. Дополнительно выделены `out` 80 МиБ и `ro` 160 МиБ (`:229–230`), веса деквантизации и промежуточные тензоры. Это не утечка между вызовами, а намеренно увеличенный пик ради перекрытия вычислений и обмена. Включение меньшего ahead требует замера производительности. При `след_куски` код принудительно запускает все куски вперёд независимо от `_ВПЕРЁД`.

### Запасные прямые ветви существуют и вне первого слоя

**Средний приоритет. Статически достижимые пути, без отдельного подтверждения OOM.**

- `fa2sm80_blockpipe.py:196–205`: неподходящая W8-проекция или отсутствие Clef range hook переводят весь блок в прямую ветку. Функция не ставит верхнюю границу M для этого пути.
- `fa2sm80_rowpipe.py:83–85`: отсутствие range hook отключает куски даже для W8; отсутствие W8 делает то же при Clef.
- `fa2sm80_blockpipe.py:181–188,381–382`: переход к следующему слою через `_след_прямо` выделяет полные `h2` fp16 и `ro2` fp32; при M=8192 и H=5120 это ещё 240 МиБ перед проекциями следующего слоя, пока вызывающий блок ещё имеет свои локальные тензоры.

Единая политика ограничения размера fallback-пути нужна для всех этих мест. Нельзя просто квантизовать первый слой или отключить Clef ради обхода ошибки без проверки качества модели.

### Подрезка аллокатора не ограничивает живую память

**Средний приоритет. Ограниченность защиты подтверждена кодом.**

`vllm/v1/worker/gpu_model_runner.py:4150–4169`: empty_cache вызывается до выполнения шага, только при числе токенов выше порога и достаточной разнице reserved − allocated. Функция не освобождает живые активации, IPC-буферы или удерживаемые графами тензоры и не повторяет проверку непосредственно перед крупным выделением внутри custom op.

След Clef корректирует порог в `fa2sm70_clef.py:268–280`, но это не заменяет бюджет рабочего набора. expandable_segments:True уже присутствует в обеих переменных окружения аллокатора. Предложение просто включить этот параметр не является новым исправлением для данного сервера.

## Что проверено и не признано утечкой

Encoder cache действительно хранит GPU outputs в `gpu_model_runner.py:2818–2819`, но имеет управление ёмкостью и освобождением: `vllm/v1/core/encoder_cache_manager.py:154–180` проверяет свободные и освобождаемые слоты, а `gpu_model_runner.py:1116` удаляет переданные на освобождение hashes. При аварии его логическое заполнение составляло около 96,8 процента. Это дополнительный рабочий набор, который нужно учитывать, но одного словаря encoder_cache недостаточно для диагноза утечки.

`eagle.py:554–570` сохраняет pad metadata по форме навсегда. При фиксированных ограничениях batch/block table это ограниченный набор, а не доказанный источник большого расхода. Удалять его отдельно от зависимых графов нельзя: код прямо исправляет прежнюю ошибку использования освобождённых адресов.

Общий буфер W8 (`fa2sm80_w8.py:301–305`) и буферы B/C blockpipe (`:137–147`) растут до максимального размера на устройство, а не по записи на каждый запрос. Они повышают постоянное потребление и могут давать transient peak при росте, но ревизия не устанавливает неограниченного роста этих словарей.

Ранее, 26–27 октября, systemd фиксировал и другие сбои `oom-kill`, связанные с обычной RAM; в unit уже есть комментарий об увеличении лимита с 14 до 21 ГиБ. Их нельзя смешивать с установленными выше CUDA OOM 27–28 октября. Последние kernel OOM в контейнере backtest относятся к другой cgroup и сами по себе не объясняют падение vLLM.

## Порядок исправлений и проверки

1. Обеспечить достаточный запас VRAM: пересчитать явный KV budget с учётом полного fallback-пика, Clef, графов MTP и encoder cache. Временное снижение batch tokens или KV bytes — меры для проверки на стенде, не применённые изменения.
2. Реализовать обработку fp16-проекций первого слоя по кускам с корректным Clef range hook. Проверить и out projection, и down projection, и переходы к следующему слою.
3. Сократить время жизни промежуточных тензоров `_прямо`; затем проверить выигрыш memory snapshot, в том числе асинхронные потоки.
4. Выделять all_gather buffer только в нужной ветке. Не менять out-of-place all_reduce на in-place без проверки aliasing, остаточных связей, регистрации custom ops и захвата графов.
5. Задать бюджет MTP-графов, считать retained bytes и аккуратно очищать неудачные captures. Безопасность адресов и общих graph pools важнее механического LRU.
6. Проверить меньший blockpipe ahead, оценив одновременно пик памяти и потерю скорости.

Проверки перед выпуском исправлений:

- Смешанный prefill/decode, шаг 8192 токена, Clef, неквантованный слой 0; отдельно M=8191/8192 и разные составы пачки.
- Успешный P2P, принудительный NCCL fallback, граница CE capacity, захват и повтор графа.
- Чередование коротких и длинных контекстов, batch sizes 1–16, изображения и новые корзины MTP; наблюдать насыщение числа графов и памяти на длительном прогоне.
- Инъекция отказа capture с проверкой освобождения частично созданных клонов и безопасного fallback.
- Побитовая сверка там, где она является контрактом существующего ядра; проверка Clef и качества после изменения границ кусков.
- Измерять одновременно driver free memory, allocated/reserved PyTorch, private pools, прямые IPC allocations, retained bytes графов и encoder cache. Одного nvidia-smi либо KV usage недостаточно.

Ревизия и расчёты выполнены по локальным исходникам, конфигурации и журналам; исправления и нагрузочные тесты остаются следующим этапом.
