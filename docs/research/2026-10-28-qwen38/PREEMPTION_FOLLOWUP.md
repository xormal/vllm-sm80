# Проверка после провала KV-boundary

28.10.2026. Локальное наблюдение: C8×(49147 входных+2048 выходных токенов), KV100%,2 preemption; один поток после двух токенов молчит600с, семь остальных продолжают медленно. После клиентской отмены скорость остальных резко восстанавливается. Данные: `state/acceptance/candidate-initial/kv-boundary`, [сводка отказа](full-validation/preemption-failure.json). Пока это доказательство длительного отсутствия прогресса, а не доказательство бесконечного deadlock.

В журнале во время медленной фазы повторяется освобождение2,2–2,4ГиБ удержанной памяти через ветку `total_num_scheduled_tokens > 512`. Следовательно, классификация этих шагов как обычного чистого decode требует проверки. Это не измерение времени ядер и не установленная первопричина. GPU0/1 при одном чтении работали вP0,1200МГц,79/74°C; полного ряда частот пока нет.

Уточнение 23:22: значение **2 preemption взято из HTTP-метрик**, оно может запаздывать. Scheduler передаёт `request.take_events()` только вместе с `EngineCoreOutput`; при пустом выходе recompute события остаются у запроса. Следовательно, молчащий поток может вытесняться снова, не увеличивая видимый счётчик. Отсутствие роста этого counter не исключает thrashing.

Конкретная гипотеза для трассы: пул внимания содержит 32 страницы с зарезервированной null-страницей. Восемь запросов после перехода через 49152 токена требуют по четыре страницы, всего 32 полезные страницы при 31 доступной, если префиксы не разделяются. Семь запросов занимают 28 страниц; оставшиеся три позволяют снова начать recompute восьмого, но не пройти границу. В waiting-ветке резервируется лишь текущий chunk, а lookahead обнуляется при `num_computed_tokens==0`. Это согласуется с повторными большими шагами и восстановлением после отмены. Пока **не подтверждено трассой**. Возможное исправление — проверять достаточность места для завершения recompute и перехода к decode перед повторным допуском вытесненного запроса, сохраняя max_num_seqs, KV budget и контекст. Нужно учитывать каждый отдельный пул, prefix hits, MTP slots и async placeholders; не заменять реальный allocator арифметикой только одной группы.

## Последовательность диагностики

1. Сравнить одинаковый вход на checkpoint351e4c74b и default-кандидате с рабочим Clef. Сохранять токены по запросам, периодический прогресс, очередь, preemption, terminal silence и ошибки; завершённые чанки не должны скрывать тайм-ауты.
2. При воспроизведении снять CPU-метаданные scheduler/runner: request ID, scheduled tokens, computed tokens до/после шага, output placeholders, prefill flag, число фактических выходов, состояние при preempt/resume, free blocks и переданный token payload. Не читать CUDA tensors на CPU в горячем пути ради этого лога.
3. По этим данным построить CPU-воспроизведение перехода состояний. Проверить согласованность scheduler-local и worker-confirmed состояний, а также восстановление GDN и границу страницы16384. Простое снижение нагрузки или отключение MTP не является исправлением принятого контракта.
4. При необходимости использовать существующий фазомер (`FA2SM70_STEP_PHASE`, `..._DEV`, `..._NOSYNC`) в отдельном диагностическом процессе. Его результаты не смешивать с обычными замерами скорости. Сначала подтвердить, какой этап шага расходует время.
5. Любая правка — отдельный runtime-коммит и повтор exact-input regression, A/B качества и скорости. Release-soak имеет смысл после устранения этого блокера.

## CPU-воспроизведение 23:31

`scripts/reproduce_preemption_cpu.py` использует настоящий Scheduler/KV allocator, локальный синтетический OPT config без весов, 32 страницы по 16384 токена, 8 запросов по 49147+2048, budget8192 и max_num_seqs16. CUDA скрыта; процесс ограничен 2 ГиБ/CPU100%/swap0. Выходы синтетические по одному токену, async/MTP/GDN здесь не моделируются.

| Режим | Все запросы завершены | Вытеснения | Запланированные повторные токены после вытеснения |
|---|---|---:|---:|
| Исходный Scheduler | 8/8 | 286 | 14045502 |
| CPU-only admission probe | 8/8 | 1 | 49152 |

Без probe последний запрос после шести токенов многократно пересчитывается; за первые 500 шагов — 64 вытеснения, 3126670 повторных токенов. Probe проверяет доступность страниц для текущей полной последовательности и следующего токена перед возобновлением. Пока это тестовая обёртка только внутри CPU-скрипта, не исправление рабочего runtime. Сравнивать число scheduler steps как скорость нельзя: шаги с тысячами prefill tokens и шаги decode имеют разную стоимость на GPU. Данные: [исходный сценарий](full-validation/preemption-cpu-complete.json), [probe](full-validation/admission-cpu-complete.json).

GPU A/B первой пары тоже завершён с отказом обоих вариантов: baseline731,03 с, candidate729,22 с; у обоих 7/8 полных ответов и пауза600 с на одном запросе. Это не производительный режим восстановления и не основание принимать текущий кандидат.

Дополнение 23:49: CPU-проба с `--lookahead 4` резервирует четыре дополнительных KV-токена, но по-прежнему генерирует синтетический одиночный выход и не моделирует MTP/GDN. Без admission за 500 шагов — 65 вытеснений, 3151225 повторных токенов; последний запрос выдаёт **два токена**, затем не продвигается. С admission, учитывающим lookahead, полный прогон заканчивается 8/8×2048 токенами, одним вытеснением и 49148 повторными токенами. Совпадение характерного симптома усиливает гипотезу, однако GPU-трасса ещё необходима.

## Внешние зацепки, проверенные28.10

- [vLLM issue63549](https://github.com/vllm-project/vllm/issues/63549) описывает ошибку восстановления token payload в Model Runner V1 при async scheduling и preemption. Там процесс падает сKeyError; у нас такой ошибки не наблюдалось. Это смежный класс состояния, не доказанная причина текущего отказа.
- [PR41177](https://github.com/vllm-project/vllm/pull/41177) предлагает учитывать подтверждённый worker batch при передаче полного token payload. PR закрыт без слияния; перенос без проверки локального async/MTP-контракта не обоснован.
- [Issue53912](https://github.com/vllm-project/vllm/issues/53912) содержит сообщения о порче генерации при prefix caching+MTP у гибридных GDN/Mamba, включая Qwen3.8-27B наAmpere. В описанных конфигурациях отличается cache mode/точность/версия; это основание расширять проверки состояния и качества, а не объявлять найденное исправление.
- [Issue54919](https://github.com/vllm-project/vllm/issues/54919) описывает многоминутное замедление decode из-за длинного prefill. Там KV не заполнен и preemption отсутствует; похожий внешний симптом не означает одинаковую причину. Наш переход KV100%→timeout→быстрое восстановление требует собственной трассы.

Ни один из этих материалов не является основанием обновлять весь vLLM или менять конфигурацию кандидата без отдельной проверки собственных ядер, ABI, GDN и Clef.

Дополнение 29.10, 00:02: в проверенном [upstream SchedulerConfig](https://github.com/vllm-project/vllm/blob/main/vllm/config/scheduler.py) есть `scheduler_reserve_full_isl=True`; [scheduler](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/scheduler.py) передаёт этот выбор в [KVCacheManager](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/kv_cache_manager.py), который проверяет полную известную последовательность перед выделением текущего chunk. В локальном форке этих полей/веток нет. Это независимая опора для направления admission-check, не готовый совместимый patch: здесь раздельные пулы с `has_free_blocks_for`, прежний async accounting, собственный GDN all-mode. Более того, проверка только `request.num_tokens` может пропустить нашу границу, если существующая последовательность ещё помещается, а следующий K4-lookahead уже требует дополнительную страницу. Нужен локальный regression с точными 49147+2048 и сохранением K4, без глобального уменьшения concurrency или увеличения KV budget.

## Отдельная численная находка

Первый валидный reference повторил большой solo/mixed logprob drift на16389: max|Δ|0,946765 при одинаковых32 выходных токенах; первоначальный кандидат дал0,943037. Это свидетельство существующего в базовой системе эффекта, а не доказательство регрессии памяти в кандидате. В первой короткой серии3/3 чатовых текстов и все их logprobs совпали с первоначальным кандидатом точно; ответы Clef также совпали.

Для атрибуции численного эффекта нужны одинаковые teacher-forced префиксы, layout target/MTP и выбранные sparse blocks. В текущем конфиге `SPARSE_DEC_GRP=0`, `TOPF=0.15`, `MINBLK=256`; `_decode_uniform` выбирает группу по числу speculative queries и агрегирует их при отборе блоков. Это одна из проверяемых гипотез зависимости распределения от способа группировки, не установленная причина найденного drift. Изменять параметры отбора илиK4 без quality/speed gate нельзя. Top20 entropy bounds и средняя MTP acceptance не заменяют такую проверку.

## Оставшееся ожидание: фрагментация страниц

В исходном attention-пуле31 полезная страница по16384 токена. Восемь независимых последовательностей по51195 токенов требуют32 страницы, хотя409560 токенов укладываются в507904 полезных токен-слота. Поэтому исправление допуска устраняет лишний пересчёт, но само не устраняет ожидание. Это внутренняя фрагментация, а не доказательство недостаточной ёмкости для полезных токенов.

CPU-эксперимент `--attention-block-size 8192` сохраняет общий объём524288 token slots с null-страницей:64×8192 вместо32×16384. При тех же8×(49147+2048),K4,batch8192,maxseq16:8/8 завершений,**0 preemption,0 recompute**,2096 синтетических шагов. [Артефакт](full-validation/pages8k-cpu.json). Это не GPU benchmark, не моделирование GDN и не изменение действующей конфигурации.

Локальный путь размера страницы: `vllm/model_executor/models/config.py`, `FA2SM70_MAMBA_BLK_MULT=8` в base config; при split pools attention block приравнивается к Mamba block. Более поздний код `kv_cache_utils.py` независимо задаёт49 GDN-блоков и отдаёт attention остаток KV budget. Эксперимент с меньшей общей гранулярностью перспективен без изменения контекста, maxseq, точности или количества KV-байтов. Но он меняет частоту GDN checkpoints и prefix-cache eviction; необходимо проверить реальные размеры/число пулов, max context, prefix reuse, async/MTP rollback, attention page transitions, slot mapping и качество на одинаковых префиксах. Не менять только attention stride без анализа совместимости всех metadata. Runtime пока остаётся на16384.
