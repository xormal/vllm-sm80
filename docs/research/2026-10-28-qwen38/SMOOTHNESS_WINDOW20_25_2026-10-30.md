## Исправления по ревизиям

1. Ячейка Clef: повтор упорядочен на карте (ожидание события tap/головы/копии перед req_begin), без ожидания хоста;
   результат головы копируется на хост сразу за головой на побочном потоке; сборщик публикует с хоста (единственный
   CUDA-вызов сборщика — опрос события, под замком захвата).
2. Файл режима (полный граф / граф has_clef / eager) — одно значение на шаг планировщика на всех рангах TP (ранг 0
   читает раз в 64 шага и рассылает по CPU-группе TP).
3. Графовая ветка асинхронной головы: tap на основном потоке только собирает строки, головы — на побочном
   (`tap(h, run_heads=False)` + `run_pending_heads()`).
4. Синхронный tap после асинхронного режима ждёт поток головы всегда.
5. Полный граф — только нативная свёртка (Triton-ветка читала метаданные в прежней нумерации строк).
6. Стенд: строгая проверка SSE, остановка клиентов Clef при любом исходе, паузы и по полным ответам.

## Инциденты окон (только A/B; боевой был остановлен)

* Окно 24: исправление публикации вынесло `ev.query()` сборщика из-под замка захвата → сорван ленивый захват графа
  MTP, испорчен пул захвата, OOM. Правило: любой CUDA-вызов из нити, кроме рабочей, — под замком захвата.
* Окно 24b: режим Marlin хранил вес двумерным — скомпилированный граф из кэша (`assert_size_stride`) отказал при старте.
* Окно 25/25b: illegal memory access в первой тяжёлой смеси (4 чата + 4 потока Clef). Деление (25b, прогон A без
  NCOMP_CPU и CONV_META) упало так же; ошибка всплывала в черновике (`eagle.prepare_next_token`). Причина: признак
  раскладки Marlin стоял ПО ФОРМЕ `(K, N)` в `_ТЮН`, а слой MTP (`FA2SM70_MTP_W8=1`) пакуется НАШЕЙ раскладкой
  (`упаковать_вне_gptq`) с теми же `(K, N)`, что MLP модели — его веса читались как Marlin, логиты черновика —
  мусор. Выход модели при этом верен (приёмка сверяет черновик точно), поэтому одиночные проверки проходили.
  Исправление: признак — у конкретного веса/слоя (`_МАРЛИН_ПТР` по `data_ptr`, `layer.fa2sm80_marlin`), `_ТЮН`
  режим Marlin не трогает. Проверка — окно 25c.
