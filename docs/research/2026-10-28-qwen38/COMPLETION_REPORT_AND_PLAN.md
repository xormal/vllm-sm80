## 3. Что остаётся нерешённым

1. **Clef всё ещё отключает граф для смешанного шага.** В `sm70/integrations/vllm_sm70/fa2sm70_clef.py::_determine_batch_execution_and_padding` устанавливается `force_eager=True`. Чат и Clef могут идти в одном target forward, но этот проход выполняется eager. Чистый подходящий decode использует CUDA graphs.
2. **Маршрутизация поправок зависит от CPU.** `set_step` хранит сегменты, C++ выбирает адреса/размеры GEMM по CPU vector, Python включает `_АКТИВЕН` только вокруг target. Эти решения не пересчитываются при replay. Простое снятие `force_eager` может применить поправки к устаревшим или чужим строкам.
3. **Подготовка и голова Clef задерживают критический путь.** Есть синхронизация при подготовке, общие scratch/stage buffers, обработка результата после forward. Асинхронность требует нового владения буферами и слотами, а не только другого stream.
4. **Запас VRAM не доказан.** Прямой NVML free после изображений опускался до 9 MiB на GPU0 и 5 MiB на GPU1. Ранняя оценка `total-used` была ошибочной: пропускала 465 MiB driver-reserved. NVML free не равен доступному для повторного использования кэшу PyTorch; нужны замеры allocator и прямых CUDA allocations.
5. **Остаются долгие паузы.** В насыщенном KV сценарии после исправления завершились 8/8 запросов, но max gap достигал 35,34 с. Изменение размера страниц проверялось CPU-пробой, GPU-приёмки и runtime-включения нет.
6. **Полное сохранение качества не установлено.** Есть logprob drift до 0,01248 на двух коротких примерах при одинаковом тексте. Четыре semantic-пробы/231 позиция дали совпадение top20 в сравнении Torch/fused metadata, но не покрывают модель целиком. MLP chunks выключены из-за изменения результатов.
7. **Нет завершённой контролируемой серии 6 h / 24 h**, общего бюджета всех graph caches и доказательства плато памяти. Доверительные интервалы ранних A/B не доказывают ни ускорения, ни нулевой регрессии.

## 4. Что означает завершённый общий граф

В поддерживаемом смешанном шаге базовые проекции target и поправки Clef исполняются в общей CUDA graph execution path; состав строк меняется через device metadata без recapture на каждый запрос. Для чистого decode сохраняется быстрый путь без лишних Clef GEMM.

Первый технический этап — mixed piecewise graphs. Если часть target остаётся eager, это явно отмечается в отчёте и измеряется; нельзя называть такой результат полностью графированным forward. Целевой полный mixed target capture оценивается после устранения динамических attention/GDN зависимостей и подтверждения бюджета памяти.

Голова Clef может оставаться отдельной асинхронной работой; MTP и sampler на первом этапе сохраняют существующие границы. Требование равномерной генерации проверяется по реальной выдаче клиенту: один большой граф сам по себе не устраняет длительность prefill и головы.

- [ ] Обработать cancel, preemption, restart записи и ошибки без смешивания накоплений или двойной публикации. CPU ready/enqueue не считать GPU completion.
- [ ] D2H результата выполнять в pinned output; сериализацию/выдачу результата вынести из model runner после completion event. Ограничить очереди и число удерживаемых buffers.
- [ ] Делить длинную голову на задания с измеренным временем: low-priority stream не прерывает уже запущенное ядро. Проверить конкуренцию за SM/HBM и задержку следующего TP collective.

**Выход:** чатовый forward не ждёт CPU-публикацию Clef; нет гонок, slot leaks и ухудшения Clef throughput. Полную резидентность весов головы (+примерно 202 MiB на rank0 относительно stage buffer) рассматривать только после освобождения бюджета.

### Этап F. Ограничить длительность смешанного шага

- [ ] Добавить в scheduler бюджет работы Clef на шаг при прежнем глобальном batch8192; обеспечить обслуживание decode и гарантированный прогресс Clef без starvation.
- [ ] Калибровать бюджет по GPU-времени для контекста/изображений, а не только числу строк. Проверить, что сокращение chunks не переключает sparse prefill/TP на более медленный или численно другой путь.
- [ ] Сравнить короткие mixed graph steps с отдельными короткими Clef slices как контрольным вариантом. Второй вариант сам по себе не завершает пункт общего графа и может проигрывать из-за повторного прохода весов.
- [ ] Отдельно проверить KV fragmentation и ожидание страницы. Изменение размера страниц принимать только после GPU-проверок всех attention/GDN/MTP mappings и качества; CPU-проба недостаточна.

**Выход:** p95/p99/max gap уменьшаются относительно baseline при сохранении chat throughput, Clef throughput/latency и устойчивой очереди. Улучшение чатов за счёт голодания Clef не принимается.

## 6. Проверки и условия завершения

Минимальные CPU-тесты до GPU: построение row descriptors и masks, slot/epoch lifecycle, cancel/preemption transitions, bucket selection и memory accounting. Они проверяют контракт; корректность CUDA replay и чисел устанавливается отдельно на GPU0–1.

| Проверка | Критерий приёмки |
| --- | --- |
| Локальная корректность ядер | Eager/replay при одинаковой форме и арифметике совпадают побитово; проверены padding, offsets, beta/bias, TP ordering и неизменность чужих строк |
| Изменение формы GEMM | Отдельно измерены drift и task quality; алгебраическая эквивалентность не выдаётся за численную. Не вводить новые допуски автоматически |
| Качество сети | Short/long reasoning, code, tools, мультимодальность, near-threshold Clef; одинаковые prompts/seeds/sampling; контроль logits, ответов и состояний |
| Энтропия | Разбивка по low/high entropy, малому top1–top2 margin и длине контекста; top-k даёт лишь границу энтропии, а не полную оценку. На доступном поднаборе сравнить полное распределение |
| MTP | Корректны acceptance/rejection и восстановление GDN/KV; ускорение не объясняется незамеченным изменением ответов или качества |
| Память | Худшие формы, image cache, новые buckets, fallback, cancel/reuse; нет OOM и роста числа allocations/graphs без выхода на плато; резерв подтверждён по обоим рангам |
| Нагрузка | C1/C8/C16 в пределах прежней KV-ёмкости, C8+Clef R1/R4, Clef 2K/8K/34K, длинные контексты, очередь40, смешанная очередь, тела60 MB+ |
| Скорость и паузы | Не менее пяти чередующихся baseline/candidate повторов; одинаковые arrivals и прогрев, интервалы неопределённости, TTFT, p50/p95/p99/max gap, per-request/aggregate tok/s, Clef req/s, backlog |
| Длительность | Контролируемый mixed soak6h, затем24h: без OOM, повреждения состояний, утечек, зависших запросов и скрытых перезапусков |
| Эксплуатация | Финальный профиль, cache fingerprint, rollback и recovery соответствуют проверенному коду; fault recovery проверена отдельно и не маскирует failures в soak |

SSE-чанк с несколькими MTP-токенами считать одним событием выдачи: искусственные нулевые интервалы между токенами чанка не улучшают p99. Считать также время ожидания и незавершённые запросы. Доверительный интервал, допускающий существенное замедление, не является доказательством отсутствия регрессии; при недостаточной точности результат остаётся неопределённым.

Идеи DFlash2 допускаются как отдельные эксперименты в существующем MTP: только с проверкой распределения вывода, состояния, качества и сквозной скорости. Внешний драфтер для исходной Qwen, обучение нового драфтера и дополнительная i8-деградация не являются необходимыми шагами этого плана. Подробности исследования: [BREAKTHROUGH_OPTIMIZATIONS.md](BREAKTHROUGH_OPTIMIZATIONS.md).

## 7. Порядок поставки и итоговые артефакты

Каждый этап — отдельный обратимый runtime-коммит с флагом включения, проверками и записью результата. Порядок: A → B → C → D → E → F → полная приёмка композиции. Подготовку CPU-части E можно вести раньше; его GPU overlap проверять только после выделения безопасного бюджета памяти.

Для завершения сохранить:

- [ ] Текущий baseline и итоговую конфигурацию с commit/ABI/cache fingerprint.
- [ ] Отчёт по graph coverage и корректности replay; перечисление оставшихся eager участков и supported shapes.
- [ ] Таблицу памяти по обоим рангам: измеренные пики, владельцы pools/scratch, резерв и плато за soak.
- [ ] Парные результаты качества по энтропии/длине/типу задачи и состояния GDN/KV/MTP.
- [ ] A/B таблицу скорости, Clef latency/throughput, межчанковых пауз и очереди с неопределённостью измерений.
- [ ] Результаты6h/24h, включая ошибки, retries, перезапуски и незавершённые запросы.
- [ ] Проверенный запуск на боевом порту, автозапуск, наблюдателя и процедуру отката по [LIVE_DEPLOYMENT.md](LIVE_DEPLOYMENT.md).

**Задачу можно закрыть только после совместного выполнения критериев памяти, качества и производительности для финального профиля.** Работа сервиса, успешный отдельный stress test, высокая MTP acceptance или включение флага CUDA graphs по отдельности этого не доказывают.
